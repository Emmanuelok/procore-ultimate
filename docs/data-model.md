# ConstructOS — Data Model Catalog

Generated by reading the Drizzle schema files in `packages/db/src/schema/`. One section per
schema file. All statements are grounded in the committed schema; where behaviour is claimed
(e.g. "never updated"), the enforcing code is cited.

## Conventions

- **IDs**: `text` primary keys, prefixed nanoids from `apps/api/src/lib/ids.ts`
  (`rfi_x7…`, `prj_…`), 21 chars ≈ 121 bits of entropy. The one exception is
  `ledger_entries.seq` (`bigserial`) — chain order must be total and gapless per insert.
- **Relationships are logical, not declared.** There are no database FK constraints;
  `*Id` columns reference other tables by convention and every access path re-scopes by
  `companyId` (and `projectId` where applicable). Relationships below use crow's-foot
  notation in prose: `A 1—n B` means one A has many B.
- **Timestamps** are `timestamp with time zone` in `mode: "string"` (ISO strings in
  application code). Date-only fields (due dates, log dates, warranty dates) are `text` ISO
  dates.
- **Enums** are stored as text; the single source of truth for members is
  `packages/shared/src/enums.ts` (renaming a member is a data migration).
- **jsonb bags** (`settings`, `metadata`, `attributes`, `sections`, `properties`) are the
  designed extension points — new per-record data goes there before it earns a column.
- **Booleans**: `identity.ts`/`documents.ts` use real `boolean`s; several later files use
  `integer` 0/1 (`isSuperseded`, `needsReview`, `aiDrafted`, …) and `twin.ts` `sensors.isActive`
  is `text "true"` — cosmetic inconsistency, noted for future normalization.
- **Multi-tenancy**: every tenant-owned table carries `companyId`; per-project tables carry
  `projectId`. Tables keyed only by record reference (`watchers`, `tagAssignments`,
  `customFieldValues`, `fileVersions`, …) are reached exclusively through a parent that was
  tenant-checked first.

## 11. Assurance — `assurance.ts`

The eight Volume III §4 primitives; mapping below. Supporting notes:

- `assertions.sourceType`/`sourceId` point back at the operational record the claim came from
  (invoice line, daily log, …) — the delivery→assurance bridge.
- `evidence.contentHash` is the sha256 anchor of admissibility; `independenceScore` (0..1)
  quantifies how independent the source is from the claimant population; `provenance` records
  every hand the artifact passed through; `submittedBy` makes the claimant/evidence separation
  checkable.
- `reconciliations` carries `method`, `result` (ReconciliationResult), `variance`,
  `variancePercent`, `confidence`, `reviewerId`, `disposition` — created via
  `POST /projects/:id/reconciliations`, which **rejects evidence wholly submitted by the
  claimant** unless explicitly overridden (`modules/assurance/index.ts`).
- `obligations` adds `warnDaysBefore` (time-bar early warning) and `satisfiedEvidenceId` —
  satisfying an obligation requires pointing at evidence.
- `signals.disposition` may only be changed by an `integrity_reviewer`
  (`requireAssuranceRole(["integrity_reviewer"])` on `/signals/:signalId/disposition`).
- `ledger_entries` rows are never updated or deleted; `seq` is `bigserial` so each company's
  chain (`companyId` + `prevHash` links) has a total order. `payload` is an optional canonical
  snapshot stored only for high-value objects (`storePayload` in `lib/ledger.ts`).

### The eight primitives — spec Vol III §4, verbatim, mapped to schema

| # | Spec definition (verbatim) | Table | Notes on fidelity |
|---|---|---|---|
| 1 | **`Assertion`** — "any claim made by any party. A quantity, a rate, a completion percentage, an entitlement, a headcount. Attributes: claimant, value, unit, basis, timestamp, contract reference." | `assertions` | All named attributes present: `claimantId`/`claimantKind`, `value`, `unit`, `basis`, `assertedAt`, `contractRef`; plus `kind` (AssertionKind) and operational source pointer. |
| 2 | **`Evidence`** — "anything that bears on whether an assertion is true. A photograph, a telematics record, a biometric log, a delivery note, a survey, an inspection, a bank transaction. Attributes: source, capture timestamp, hash, provenance chain, independence score." | `evidence` | `source`, `capturedAt`, `contentHash`, `provenance`, `independenceScore`; `kind` covers the spec's example list exactly (see `EVIDENCE_KINDS` in `packages/shared/src/enums.ts`). |
| 3 | **`Reconciliation`** — "the join between assertion and evidence. Attributes: method, result, variance, confidence, reviewer, disposition. **This is the product. Everything else is scaffolding around this table.**" | `reconciliations` | All six attributes as columns (+`variancePercent`, `notes`). Evidence set as `evidenceIds` jsonb[]. |
| 4 | **`Obligation`** — "a contractual duty. Attributes: source clause, obligor, obligee, trigger, deadline, evidence requirement, status. Time bars are `Obligation` records with a computed deadline." | `obligations` | All attributes present; `warnDaysBefore` implements the time-bar early warning; `/obligations/upcoming` surfaces approaching deadlines. |
| 5 | **`Event`** — "something that occurred. Attributes: type, timestamp, location, detected-or-reported, causal links. Delay events, integrity signals, incidents and instructions are all `Event` subtypes." | `events` | `type`, `occurredAt`, `location`, `detectedOrReported`, `causalLinks` jsonb[] + free `payload`. Subtyping is by `type` string at this phase. |
| 6 | **`Entity`** — "any legal or natural person. Attributes: identifiers, jurisdiction, relationships, roles, screening status. The graph over this object is what makes collusion detection possible." | `entities` + `entity_relationships` | Relationships are typed edges (`ENTITY_RELATIONSHIP_KINDS`: director_of, beneficial_owner_of, shares_bank_account_with, …) with `confidence` and `source`; `GET /entities/:id/graph` walks the graph. `vendors.entityId` mirrors delivery-side vendors in. |
| 7 | **`Signal`** — "a detected anomaly. Attributes: detector, severity, confidence, supporting evidence set, false-positive feedback, disposition, escalation state." | `signals` | `detector`, `severity`, `confidence`, `evidenceRefs`, `disposition` (includes `false_positive` and `escalated` members), `reviewerNotes` as the feedback channel. Emitted by `modules/assurance/detectors.ts` + `modules/drawings/detectors.ts`. |
| 8 | **`Ledger Entry`** — "the append-only, hash-chained record of every state change to any of the above. Never updated, only appended. This is what makes the system's output admissible rather than merely informative." | `ledger_entries` | Chain semantics implemented in `packages/ledger/src/chain.ts`; appended by every module via `lib/ledger.ts`; verified via `GET /ledger/verify`. |

**Design rule (spec §4, verbatim):** "`Assertion` and `Evidence` must never be created by the
same actor through the same pathway. The moment the contractor can author both sides of a
reconciliation, the product is worthless. This constraint is the entire architecture."
Current enforcement: `evidence.submittedBy` and `assertions.claimantId` are always recorded;
reconciliation creation rejects evidence sets wholly submitted by the claimant (only an
`integrity_reviewer` may knowingly override); obligation satisfaction records a
`selfCertified` flag in its ledger payload. Full pathway-level
separation (independent ingestion channels) is Tier-1 roadmap work — see `docs/roadmap.md`.
